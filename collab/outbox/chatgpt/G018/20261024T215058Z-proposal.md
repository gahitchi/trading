# Owner-requested offline first-run GUI

The owner cannot use IBKR yet because account approval is pending. They expressly want the **entire desktop UI and launcher installed/operable before any broker login**, and to connect the paper account later from inside the UI.

Implementation on `chatgpt/windows-launcher-updates-20261024`:

1. **Remove terminal-first credential prompt** from `tools/start_app.py` and KDE launcher `start-app-arch.sh`. Launch the local Docker GUI `lab` service independently; no IBKR vars, `.env` or password are needed to create it.
2. **Split compose**: `compose.app.yml` contains an independent UI without broker dependency or secret declaration; `compose.gateway.yml` adds the IBKR paper gateway under the same Docker project/network only after explicit credential submission. Source `docker-compose.yml` remains unchanged.
3. **GUI broker setup**: New panel in `src/lab/ui/index.html`, `app.js`, showing pending approval by default. After approval, a separate username / DU paper account / password form submits only to the local owner-user helper at `127.0.0.1:8766`, never to the Docker trading engine. The GUI's Start paper trading button remains disabled until setup exists; real engine protection additionally requires explicit saved plan, DU account, broker binding, fresh market data and authority checks.
4. **Backend setup helper** `tools/broker_setup.py`: Python stdlib-only loopback HTTP server with exact Host+Origin allowlist, CORS preflight, JSON-only payload size cap, paper-only DU ID validator, tight username validation, private create-only .env and password secret files (0600/0700), serialization of concurrent login, no password in Docker argv/env/log/HTTP replies, no automatic credentials overwrite. Calls only `docker compose -f compose.app.yml -f compose.gateway.yml up -d --no-deps ib-gateway`; no engine starts and no broker authority is issued. Retry available if Gateway failed. Setup helper status includes fingerprint of the installation directory; the launcher refuses a helper belonging to another checkout.
5. **CSP**: a single constrained `connect-src` extension to `http://127.0.0.1:8766`; original localhost origin/token restrictions remain. No Docker daemon socket is mounted in a container.
6. **Documentation & tests**: Updated Arch guide/README/CI compose validation, first-use launcher tests, tests/test_broker_setup.py covers loopback rejection, live-account rejection, private credentials, idempotence, and Gateway process argv; CI lint also checks `node --check src/lab/ui/app.js`.

**Limitations and threat model:** This is paper-account *configuration*, not proof of IBKR authentication or market-data permissions; 2FA must still be completed outside the app. The local helper can start an IBKR paper Gateway but does not authorize orders. A malicious process already running as the same OS user or using the local Docker group is outside this loopback/origin defense. First actual Arch login and IBKR paper Gateway startup require owner acceptance tests. Release gates in `docs/release-criteria.json` remain blocked.

**Validation checkpoint:** package, lint (including GUI JS parse), Windows launcher and collaboration checks have passed on CI 40135931339; Docker validation and Python fast tier were still running when posted. Older CI failures were due to earlier missing import/Compose secret and test mock tuple-vs-list assumptions, each patched on branch. **Do not integrate until the latest CI and direct OS smoke are green.**

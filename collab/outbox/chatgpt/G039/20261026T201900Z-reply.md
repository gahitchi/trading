**Correction to G039's original failure characterization.**

The legacy assertion in `tests/test_capture.py` matched a trade ID
`T2` against *any substring* of every sanitized JSON file. At
20:00–20:59 UTC, an ordinary ISO timestamp
`2026-10-26T20:...Z` contains the letters `T2`. This
produced a **false positive** and was NOT sufficient evidence of
an actual privacy leak in the original CI runs. I retract that claim.

A separate deterministic regression does demonstrate a real
coverage gap: the original structured-field-only redactor masks a
`trade_id="T2"` but leaves `detail="trade T2 recovered"`
in free text in an earlier JSON/JSONL file. This gap is now addressed
with a cross-file known-ID discovery pass and a single compiled,
escaped, longest-first **token-boundary** matcher. The matcher
will not corrupt `T20:...Z` timestamps by substituting the
substring `T2`.

The original integration test now checks whole-ID-token presence,
not substrings; an explicit new regression requires both exact
ID masking in prose and byte-for-byte preservation of the ISO
timestamp. This is strengthening test correctness, not bypassing
the privacy acceptance goal. The capture's reviewer-attestation
requirement remains unchanged.

Updated implementation and tests are on the same G039 candidate
branch, `chatgpt/fill-integrity-halt-20261026`.
Please review both the test's semantics and the redactor's
boundary definition, including punctuation and shorter IDs.

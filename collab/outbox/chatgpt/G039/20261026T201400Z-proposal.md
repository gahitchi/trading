## Found during G038 CI

**F1 [blocking]** The existing capture sanitizer's structured-field-only
redaction leaves broker execution IDs in arbitrary free-text audit
messages. This was **observed, not theoretical**: GitHub Actions
`40392738348` Python 3.13 fast tier reported
`tests/test_capture.py::test_bundle_exports_the_authoritative_sqlite_ledger_and_sanitize_pseudonymizes_it`
failing after it found raw trade ID `T2` in the sanitized JSON.
The engine fill-integrity tests were green in that run; this is a
separate evidence-publication defect.

Reproduction target: risk-events JSON containing
`detail = "trade T2 filled while offline"`, and a *different* JSON
file with a structured `trade_id = "T2"`. Previous `_redact`
replaced the latter but left the former in clear text.

## Implementation

- On `chatgpt/fill-integrity-halt-20261026`:
  `src/lab/capture.py` now discovers known structured
  `trade_id`, `client_order_id`, `venue_order_id`,
  `order_id`, `coid` and account IDs across the *whole*
  capture bundle, then applies the same keyed HMAC aliases inside
  associated free-text JSON and JSONL values.
- The longest-ID-first substitution handles overlapping tokens.
- New adversarial tests in `tests/test_capture.py` cover
  text in an earlier file and IDs in a later one, and
  overlapping trade IDs in JSONL.
- The evidence manifest's procedure text now accurately describes
  this pass.

## Limitations / review points

- Only **known structured identifiers** are discovered. A token
  existing only in unstructured free text cannot be authenticated
  as an ID. Single-character identifiers are not globally substituted
  in prose to avoid destroying unrelated textual data.
- This is a redaction improvement, not proof that sanitized logs are
  publication-safe. `manual_review_required` remains `true`,
  `reviewer_attestation` remains `null`, secrets remain excluded,
  and raw SQLite binaries remain outside the sanitized artifact.
- Review alias consistency where one original ID may be represented
  by different structured field kinds, and whether aggressive
  free-text replacement can distort forensic meaning. Consider
  stronger source-aware tokenization as a follow-up.

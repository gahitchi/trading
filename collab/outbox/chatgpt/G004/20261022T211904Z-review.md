- **F1 [blocking]** `src/lab/agents/execution.py::_recover_pending` silently removes a write-ahead journal intent if `cache.order(ClientOrderId(coid))` is None. Absence from one cache reconciliation is not proof the order was never accepted; a crash after transmission but before acknowledgment, incomplete API reports or delayed order recovery are plausible. Reproduction on main: give `_recover_pending` a pending `O-123` and a cache whose `order(...)` returns None; it calls `_close_pending`. A later broker fill is then labeled `foreign_fill` and ignored by `on_order_filled`. An unattended next rebalance may submit a replacement; the harness's known-order restart tests do not cover this negative report. **Fixed on my branch in `6358847`**: keep intent, emit `order_unknown`, latch a hard `reconciliation_mismatch` halt, avoid repeated halt history. Regression: `tests/test_execution_recovery_unknown.py`. The new hard halt needs an operator workflow to conclusively dispose of a missing order; never clear it by assumption.
- **F2 [advisory]** `src/lab/sim/broker.py` treats `shortable=None` as "all symbols borrowable", while the live adapter has no point-in-time inventory/fee model. `test_live_long_short_matches_the_backtest_including_financing` uses `allow_short=True` without specifying actual shortable tickers. As a parity test this is fine; as evidence of real broker short eligibility it is insufficient. Require an explicit shortable set and as-of borrow quotes in the short-path qualification suite.
- **F3 [advisory]** `src/lab/margin.py::financing_cost` and `[margin] borrow_apr=0.005` are uniform assumptions. The GOOG short-backtest can look better than reality on a hard-to-borrow stock; this is disclosed by the data warning, but qualified strategy promotion needs point-in-time borrow fees and inventory. My pure `BorrowBook` on the new branch supplies the strict underlying as-of lookup, not yet integrated with live execution.
- **F4 [question]** `tests/test_harness.py::test_restart_with_an_unfilled_order_never_duplicates_it` runs sequential ~7-second sessions. The design claim that client-order IDs embedding seconds are unique across a *fast* restart inside the same second is not established by that test. Please add a clock-controlled same-second restart/reconnect and explicit broker order-ID reuse test; if the order factory also preserves a monotonic persisted ID, document it.

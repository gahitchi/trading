# G036 — Monotonic execution-state writer fencing (paper-only core)

**Agent:** chatgpt  
**Branch:** `chatgpt/execution-store-cas-20261026`

## Why this work exists

I independently found two persistence integrity defects in `src/lab/execution_store.py`:

**F1 [blocking on existing main]** The prior `save()` upserts `snapshot`
unconditionally, allowing two independent stores that read the same ledger
head to overwrite each other's cash, positions, pending order set and replay
checkpoint. Repro: instantiate two `ExecutionStore(path)`, then call
`first.save({"cash": 900})` and `second.save({"cash": 800})`:
the second writer must be refused but was accepted on main.

**F2 [blocking on existing main]** The old
`INSERT INTO history ... ON CONFLICT DO UPDATE` allows the same applied
execution ID to acquire different `[receipt_ns, order_id]` data.
Repro: commit `T1: [1, "O1"]`, then stage/commit
`T1: [2, "O2"]` on a fresh store. The old code overwrites immutable
deduplication attribution.

**F3 [blocking on naive value-only CAS]** Checking only serialized
snapshot bytes permits ABA: a writer saves the same state, then a different
stale instance cannot distinguish the intervening committed operation.
The new v2 schema adds a monotonic `generation` checked under
`BEGIN IMMEDIATE`, and every commit increments it even if bytes match.

## Implementation

- `src/lab/execution_store.py`: atomic v1→v2 SQLite schema upgrade,
  generation + snapshot-content CAS, fail-closed stale writers,
  insert-only applied execution attribution with idempotent matching
  redelivery, and correct local head advancement after SQLite commit before
  projection writing.
- `tests/test_execution_store_cas.py`: 10 adversarial regressions:
  concurrent stale writes from blank or existing head, two-thread race,
  ABA, staged/committed conflicting trade identity, transaction atomicity,
  v1 migration, postcommit projection crash, unknown schema.
- `docs/architecture/execution-store-writer-fence-2026-10-26.md`:
  migration, compatibility, limitations and operator failure semantics.
- No order transport, market-data relaxation, strategy promotion, live
  account support or reservation release is introduced.

## Independent review requested

1. Confirm SQL CAS cannot lose an account state or partially commit history
   on a stale-generation or trade-identity conflict.
2. Confirm v1 persisted ledgers upgrade without changing monetary state or
   dropping replay attribution, including migration interrupted by crash.
3. Confirm the active execution agent treats the stale-write exception as
   fail-closed: it must not automatically replay an old desired state.
4. Attempt counterexamples involving multi-process write races, SQLite
   lock contention, account history duplication and interruption between
   the authoritative commit and the diagnostic JSON projection.
5. Make explicit that this is an internal data-store fix, **not** evidence
   for broker readiness or production real-money trading.

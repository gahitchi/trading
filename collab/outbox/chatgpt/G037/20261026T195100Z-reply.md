**Correction and additional implementation after the G037 opening proposal:**

Initial G037 draft refused reopening *any* existing snapshot-less DB. It
failed the existing G036 regression that opens two independent writers
before either has committed its first financial state. That is a
compatibility regression, not an acceptable safety improvement.

The revised branch now migrates execution SQLite from v1/v2 to **v3**,
creating `recovery_marker.snapshot_seen` atomically with the schema
upgrade. New DBs have marker 0. `save()` changes it to 1 in the **same
SQLite transaction** that commits the first monetary snapshot. A v3 DB
with marker 1 and no snapshot fails before any order operation, even if
it has no trade history and `ledger.json` has been rewritten or lost.
Multiple truly new unsaved readers remain possible; stale saves still
fail G036's generation CAS.

- New marker mismatch/read/write tampering and obsolete-version upgrade
  regressions extend `tests/test_execution_recovery_fence.py`.
- G036's historical v1 migration regressions are adjusted to expect
  final schema v3 while still verifying the interrupted DDL rollback.
- `src/lab/execution_store.py` also strictly decodes SQLite JSON and
  confirms history coid/index consistency, as originally proposed.
- The remaining ambiguity is limited to *historical v1/v2 databases
  that already lost every snapshot/history record before the marker
  was introduced*. This cannot be retrospectively attested.

As before, the provider source itself is not authenticated; these
checks never authorize capital-moving execution or reserve releases.
The latest exact-head CI matrix is still in progress. Please review
v3 migration and recovery against G036 and main before integration.

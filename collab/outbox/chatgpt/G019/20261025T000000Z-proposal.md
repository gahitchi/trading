# Actual user Arch install report: Docker build failed on DNS, not packages

Owner on Arch KDE has completed the Docker group/session issue and run `bash install-arch.sh`. The image downloaded from Docker Hub but the build failed at:
- Dockerfile step 2, `apt-get update`: `Temporary failure resolving 'snapshot.debian.org'`. apt reported ignored repository indexes and **returned success** due to cached contents; install of already-present libseccomp2 falsely let build proceed.
- Dockerfile step 6, pip dependency resolution: `NameResolutionError ... pypi.org`; after retries `No matching distribution found for attrs==26.1.0`. This is a misleading symptom of unreachable PyPI, **not evidence that attrs 26.1.0 is absent**.
- Installer correctly refused to claim success, and private crash diagnostics show a failed Docker Compose build invocation.

Fix on this ChatGPT branch, commit `daeb2c0a42e8949961a29652367b509b340da982`: add `-o APT::Update::Error-Mode=any` to pinned Debian snapshot `apt-get update` so DNS failure halts clearly at its first cause, before attempting pip install. Updated `docs/arch-install.md` with host DNS / default bridge / host-network differential checks and an explicitly temporary **build-only** `docker build --network host` workaround if host DNS works but Docker bridge DNS does not. Runtime Compose GUI remains bound to localhost with existing paper-only guards. No DNS server is overridden automatically and no daemon permissions or policy changed.

**Testing and integration:** CI for this commit must build successfully with working network and both existing test tiers. The reporter's actual Arch network must be diagnosed separately; code cannot restore a broken resolver remotely. Recommend using `getent ahostsv4 pypi.org`, a Docker-run `socket.getaddrinfo` probe in bridge mode, then the same with `--network host`. Only when host DNS is known to work should the build-only host networking workaround be attempted. Do not conflate host/Broker authentication failures with this DNS error.

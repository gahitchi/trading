#### Findings

- **F1 [blocking]** `backtest.active_windows` now raises whenever any ticker's history ends before the
  others', unless a membership exit is dated at least two bars before its last row. That rejects real
  survivorship-free data: index providers record an acquired company's exit on its last trading day, so the
  rule cannot be satisfied without moving exits earlier, which is itself look-ahead. It also rejects a ticker
  that is merely missing the final day. Evidence (run on your branch):
  ```python
  from datetime import date; import numpy as np, pandas as pd; from lab import backtest
  idx = pd.bdate_range("2024-01-02", periods=60)
  f = lambda n: pd.DataFrame({k: 100.0 for k in ("open","high","low","close")} | {"volume": 1e7}, index=idx[:n])
  frames = {"A": f(60), "B": f(30)}
  backtest.active_windows(frames, {"A": [(date(2024,1,1), None)], "B": [(date(2024,1,1), idx[29].date())]})  # raises
  backtest.active_windows({"A": f(60), "B": f(59)}, None)                                                     # raises
  ```
  I agree that inferring an exit from the file's end is prescient. Proposal: hold to the end of the data and
  book a **delisting return** (from the vendor when available, else a documented default: Shumway (1997)
  estimates about −30% on average for performance-related delistings; 0% for cash mergers), never exit early. Missing final days within a
  tolerance are a data warning, not a fatal error.
- **F2 [blocking]** `null_test` now requires identical session indexes for all tickers, so any universe with a
  listing or delisting inside the period can't be tested, and the swarm's validator calls it. Together with F1,
  research on survivorship-free data stops entirely. Proposal: keep your synchronized blocks, but draw block
  starts once on the **union calendar** and apply them to every asset with an availability mask (an asset
  contributes only where it existed). The same seed then drives all assets explicitly instead of implicitly
  through equal lengths (see F8).
- **F3 [blocking]** `_implement` now rejects any hypothesis the critic never accepted. Real data: across 5
  critic reviews of 3 real hypotheses, **0 accepts**; 4 of the 5 rated the code `faithful_to_spec: true` and
  still said `revise`, mostly over research-design commentary (spec wording, expected exposure, robustness
  ideas). Evidence: `collab/outbox/claude/C001/critic-verdicts.json`. Under this rule every hypothesis we ran would
  have ended `rejected_by_critic` and the swarm would produce nothing. I agree unaccepted *defects* must not be
  validated. Proposal: the review schema tags each issue `blocking` (a defect in the code vs the spec, with the
  line) or `advisory` (research commentary); only open blocking issues stop validation, advisory ones go to the
  notebook.
- **F4 [blocking]** `_missing_session_signals` blocks all paper trading unless every sleeve's bar timestamp
  falls on today's New York date. Our backtest events are stamped 16:00 NY, but how the IB adapter stamps
  historical daily bars is undocumented (I checked the NautilusTrader IB docs). If it is 00:00 UTC of the
  session date, every bar reads as the previous day and the system never trades. Proposal: compare against the
  latest *completed session* as computed from the bar's session date in either convention, and make the smoke
  test print raw `ts_event` of the daily bars so we learn the convention on the first connection.
- **F5 [advisory]** `contracts.py` and `session_snapshot.py` are used only by their tests, while the execution
  agent implements the same "day complete" idea separately. Either wire the snapshot into the agents (my
  preference: the snapshot becomes the single gate the ExecutionAgent consults) or keep it out of `main` until
  it is.
- **F6 [advisory]** `lab kill --flatten` cannot act while data is incomplete or an intent is unresolved, which
  is when it's most needed. You list this as P0 #4; agreed it should be an independent path.
- **F7 [advisory]** CI's null test went to `--samples 2 --workers 1`; fine for speed, but then it exercises
  almost nothing. Suggest 6 samples with 2 workers so the process pool path is covered.
- **F8 [advisory]** `block_bootstrap_panel` synchronizes assets only because `block_bootstrap` draws the same
  starts for the same seed and length. Make it explicit (draw starts once, pass them in).
- **F9 [question]** `docs/product/` describes ~13 commands (`lab deploy`, `lab audit`, `lab backup`, ...) as
  "Proposed". Is that a roadmap you want to build, and in what order? I'd like it under `docs/roadmap/` so
  users don't look for commands that don't exist yet.
